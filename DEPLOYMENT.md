# Доставка на Finland и сохранённые плейлисты

## Что происходит при push

Workflow `.github/workflows/delivery.yml` проверяет код и собирает Docker-образ.
После успешных проверок ветки `dvizhuha` Ansible доставляет именно этот образ
на `212.192.8.121` в `/opt/discord-bot` и перезапускает `notorious-bot`.
Pull request запускает проверки без доставки. Доступен и ручной запуск
workflow с выбранной веткой `dvizhuha`.

Проверки: unit-тесты, синтаксис Python/Ansible, сборка, импорты внутри образа,
отсутствие `.env`, cookies и локальных данных в образе. Образ помечен SHA
коммита; сервер проверяет SHA и контрольную сумму архива. Новый контейнер
должен подключиться к Discord и стать healthy за 180 секунд. При ошибке
скрипт пытается вернуть предыдущий образ и проверяет его здоровье; job
остаётся красным даже после успешного отката.

## Однократное включение GitHub Actions

Эта настройка даёт GitHub возможность подключаться к Finland по SSH и запускать
Ansible. Ваш компьютер и WSL после настройки могут быть выключены: workflow
работает на временной машине GitHub. Устанавливать Ansible на Finland не нужно.

Все команды ниже выполняйте **в терминале WSL (Bash), не в PowerShell**.
Нужны доступ к настройкам репозитория и уже работающий SSH-доступ к
`root@212.192.8.121`. Команды приведены для ручного выполнения;
наличие инструкции в репозитории само по себе ничего не настраивает.

### 1. Создать окружение production в GitHub

Откройте [Settings → Environments](https://github.com/Shad0w1616/discord_bot/settings/environments)
и нажмите **New environment**. Введите имя **`production`** и нажмите
**Configure environment**. Имя должно совпадать с `environment: production`
в `.github/workflows/delivery.yml`.

В **Deployment branches and tags** выберите **Selected branches and tags**,
добавьте правило для **Branch** с именем **`dvizhuha`**. Это ограничит ветку,
которая может использовать окружение. Для полностью автоматической доставки
не включайте **Required reviewers** и таймер ожидания: иначе запуск будет ждать
подтверждения или окончания таймера.

Ниже, в **Environment secrets**, позже добавим два секрета через **Add secret**.
Нужны именно Secrets, а не Variables. Если раздел недоступен, проверьте свои
права и тариф: для приватных репозиториев доступность окружений и их секретов
зависит от плана GitHub. Подробности — в
[документации окружений GitHub](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments).

### 2. Создать отдельный SSH-ключ для доставки

Ключ состоит из двух файлов: публичный `.pub` разрешает вход на сервер,
а приватный файл без расширения позволяет GitHub этим разрешением пользоваться.
Создаём отдельную пару, чтобы при необходимости отозвать доступ Actions,
не затрагивая ваш обычный SSH-ключ.

```bash
mkdir -p ~/.ssh
chmod 700 ~/.ssh
ssh-keygen -t ed25519 -C 'github-actions-discord-finland' \
  -f ~/.ssh/discord_bot_actions -N ''
```

Пустой пароль (`-N ''`) нужен для входа без участия человека. Если `ssh-keygen`
сообщает, что файл уже существует, **не соглашайтесь на перезапись**:
используйте уже подготовленную пару или выберите другое имя во всех командах.

Добавьте публичную часть на сервер через существующий SSH-доступ:

```bash
ssh-copy-id -i ~/.ssh/discord_bot_actions.pub root@212.192.8.121
```

Команда добавляет ключ в `/root/.ssh/authorized_keys`, сохраняя прежние записи.
Для этого подключения может потребоваться ваш обычный SSH-ключ или пароль
сервера. Затем проверьте вход именно новым ключом, без запроса пароля:

```bash
ssh -i ~/.ssh/discord_bot_actions -o IdentitiesOnly=yes \
  -o BatchMode=yes -o StrictHostKeyChecking=yes root@212.192.8.121 \
  'echo SSH_OK'
```

Ожидаемый ответ — `SSH_OK`. При `Permission denied (publickey)` сначала
исправьте установку ключа: GitHub с тем же ключом тоже не подключится.
Деплой использует root, как текущий Ansible inventory; приватный ключ даёт
административный доступ к Finland. Храните его вне проекта и передавайте
только в секрет GitHub, не в Git, issues или чат.

### 3. Добавить DEPLOY_SSH_KEY

В WSL скопируйте приватный ключ в буфер обмена Windows:

```bash
clip.exe < ~/.ssh/discord_bot_actions
```

Вернитесь в **Settings → Environments → production → Environment secrets →
Add secret**. В поле **Name** укажите `DEPLOY_SSH_KEY`, в **Value** вставьте
содержимое буфера и сохраните. Вставляется **весь многострочный приватный ключ**,
включая строки `-----BEGIN OPENSSH PRIVATE KEY-----` и
`-----END OPENSSH PRIVATE KEY-----`, без дополнительных кавычек.
Файл `.pub`, путь к файлу и пароль сервера сюда не подходят.

Если `clip.exe` недоступен, откройте файл в локальном редакторе и скопируйте его
содержимое. После вставки замените содержимое буфера обычным текстом.
GitHub не показывает сохранённое значение: для исправления используйте Update.

### 4. Добавить DEPLOY_KNOWN_HOSTS

Этот секрет отвечает на другой вопрос: «подключаемся ли мы к правильному
серверу?». Он содержит публичный **ключ сервера**, а не созданный выше ключ
пользователя. Возьмите запись из WSL, откуда уже проверенно подключались к Finland:

```bash
ssh-keygen -F 212.192.8.121 -f ~/.ssh/known_hosts
```

Должна появиться как минимум одна запись, помимо строк-комментариев с `#`.
Если записи нет, сначала выполните обычное SSH-подключение и сверьте показанный
отпечаток с ключом в доверенной консоли сервера у провайдера. В этой консоли
публичный отпечаток ED25519 можно посмотреть командой:

```bash
ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub
```

Это **единственная команда в этом подразделе, выполняемая на сервере**,
через доверенную консоль. После проверки сохраните ключ при SSH-подключении
из WSL. Не заменяйте проверку слепым доверием к результату `ssh-keyscan`.

Когда проверенная запись есть, скопируйте её без комментариев:

```bash
ssh-keygen -F 212.192.8.121 -f ~/.ssh/known_hosts | sed '/^#/d' | clip.exe
```

Создайте второй **Environment secret** с именем `DEPLOY_KNOWN_HOSTS` и вставьте
запись целиком. Допустимы несколько записей для этого адреса. Хешированный адрес
вида `|1|...` тоже подходит. Один IP или отпечаток `SHA256:...` вместо полной
строки не подойдёт. `StrictHostKeyChecking` отключать не нужно.

### 5. Проверить готовность сервера

Из WSL запустите проверку наличия файлов и инструментов. Она не выводит токен
бота или cookies:

```bash
ssh -i ~/.ssh/discord_bot_actions -o IdentitiesOnly=yes \
  -o BatchMode=yes -o StrictHostKeyChecking=yes root@212.192.8.121 \
  'set -e; test -s /opt/discord-bot/.env; test -f /opt/discord-bot/cookies.txt; docker compose version; python3 --version; echo SERVER_READY'
```

Ожидайте версии Docker Compose и Python, затем `SERVER_READY`. `.env` и
`cookies.txt` остаются в `/opt/discord-bot` на сервере; workflow их не создаёт
и не скачивает из GitHub. Проверка подтверждает наличие файлов, но не срок
действия токена и cookies.

В `deploy/inventory.ini` уже указаны `212.192.8.121`, пользователь `root` и
`/usr/bin/python3`. По умолчанию используется SSH-порт 22. Он должен быть
доступен не только вашему компьютеру, но и GitHub-hosted runner. Если firewall
разрешает SSH лишь с вашего домашнего IP, потребуется отдельно настроить
доступ для выбранного способа запуска Actions.

### 6. Опубликовать изменения и проверить первый запуск

Сначала настройте оба секрета, затем отправьте изменения с workflow и каталогом
`deploy/` в ветку `dvizhuha` обычным commit/push. Если коммит уже создан
локально в этой ветке, отправка из каталога репозитория выглядит так:

```bash
git push origin dvizhuha
```

Push не отправляет незакоммиченные файлы. Не добавляйте в коммит SSH-ключи,
`.env`, cookies или данные бота.

Откройте [Actions репозитория](https://github.com/Shad0w1616/discord_bot/actions)
и запуск **Test and deploy bot** для нужного коммита. Сначала должна стать
зелёной job **test-and-build**, затем **deploy-finland**. В журнале доставки
должна появиться строка `Deployed and healthy: <SHA>`. Во время замены контейнера
музыка прервётся, после запуска бот синхронизирует slash-команды.

Если ранее запуск упал из-за отсутствующих секретов, после их добавления
откройте этот запуск и используйте **Re-run failed jobs**. Если артефакт уже
удалён (он хранится 3 дня), перезапустите все job через **Re-run all jobs**.

Для ручного запуска выберите workflow → **Run workflow** → ветку `dvizhuha`.
Кнопка доступна, когда файл workflow присутствует также в default branch
репозитория. Если её нет, первый запуск выполняйте через push в `dvizhuha`;
не требуется менять default branch ради настройки. См.
[инструкцию ручного запуска GitHub](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/manually-run-a-workflow).

После успешной доставки можно сверить серверный SHA с коммитом в Actions:

```bash
ssh -i ~/.ssh/discord_bot_actions -o IdentitiesOnly=yes \
  -o BatchMode=yes -o StrictHostKeyChecking=yes root@212.192.8.121 \
  'cat /opt/discord-bot/deployed-revision'
```

### Если запуск не прошёл

| Сообщение или ситуация | Что проверить |
| --- | --- |
| `Missing production secret ...` | Оба секрета созданы именно для `production`, имена совпадают с инструкцией, значения не пустые. |
| `Permission denied (publickey)` | Публичный ключ добавлен root на Finland, а в `DEPLOY_SSH_KEY` вставлен соответствующий приватный ключ целиком. |
| `Host key verification failed` | В `DEPLOY_KNOWN_HOSTS` есть полная проверенная запись для `212.192.8.121`; при смене ключа сервера сначала подтвердите её причину. |
| SSH connection timed out | Доступность сервера и порта 22 из runner, правила firewall. |
| Job ждёт approval или отклонена окружением | Required reviewers и правило ветки `dvizhuha` в `production`. |
| `test-and-build` красная, доставки нет | Откройте первый упавший шаг проверки или сборки; до его исправления сервер не обновится. |
| `deploy-finland` пропущена | Доставка разрешена только для `dvizhuha`, кроме запусков pull request. |
| `New container did not become healthy` | Бот не подтвердил готовность за 180 секунд; смотрите причину запуска контейнера и результат попытки отката в журнале доставки. |

Если Actions полностью отключены, проверьте **Settings → Actions → General**
и разрешение используемых `actions/checkout`, `setup-python`, `upload-artifact`
и `download-artifact`. Для этого workflow достаточно `contents: read`;
выдавать токену Actions право записи в репозиторий не требуется.

## Данные и эксплуатация

Имена существующих Docker volumes для `/app/data` и `/tmp/yt-dlp` берутся
из работающего контейнера. Очередь, настройки ежедневной рубрики и плейлисты
сохраняются между обновлениями. Если вместо named volume используется bind
mount, доставка остановится до пересоздания контейнера: потребуется явно
адаптировать конфигурацию. Делайте резервные копии volume с `/app/data`.

SQLite-файл плейлистов: `/app/data/playlists.sqlite3`. Новая функция не меняет
формат прежних данных, поэтому откат образа совместим с этим обновлением.
Откат не откатывает данные; будущие миграции должны сохранять совместимость.
Во время пересоздания контейнера музыка прерывается.

В `/opt/discord-bot/deployed-revision` записывается SHA последнего успешного
деплоя. В `releases/<SHA>/compose.json` остаётся конфигурация запуска,
при откате — `rollback.json`. Загруженный архив удаляется после успеха.
Образы старых выпусков автоматически не удаляются: периодически удаляйте
ненужные образы после проверки, оставляя текущий и образ для отката.

Прежний WSL-плейбук собирает другой образ из Git. Не запускайте его параллельно
с новым workflow; для ручного восстановления используйте сохранённый Compose
с тем же именем проекта. Новый deploy не выполняет `git clean` на сервере.

## Плейлисты в Discord

- Кнопка **💾 В плейлист** под текущим треком открывает ввод названия.
  Если плейлиста нет, он создаётся. Сохраняется трек на момент нажатия,
  включая музыку из волны. Нужно находиться в голосовом канале бота.
- `/playlist create name` — создать пустой плейлист.
- `/playlist list` — мои плейлисты на этом сервере.
- `/playlist show name page` — треки, по 10 на странице.
- `/playlist play name` — добавить сохранённые треки в обычную очередь.
  Сначала остановите волну, если она играет.
- `/playlist remove name position` — удалить трек по номеру.
- `/playlist delete name confirm:true` — удалить плейлист.

Плейлисты личные, отдельно для каждого сервера. Лимит: 25 плейлистов по
200 треков; одинаковый URL дважды не добавляется. Названия не чувствительны
к регистру. Новые slash-команды синхронизируются при запуске бота.
